# 国内个人 Agent 使用场景与办公连接器调研

日期：2026-10-04 · 状态：公开能力调研与产品假设，尚未接入真实账号或进行用户访谈

配套见 [PRD](./PRD.md)、[技术架构](./ARCHITECTURE.md)、[dots 对标](./DOTS_BENCHMARK.md)。用户方向仍为国内大众个人用户、生活助理优先；本轮增加企业微信 / 飞书入口与其他场景评估，不把产品整体改成企业管理系统。

## 1. 产品判断

建议把产品主线扩展为 **“个人事项助理：从消息和资料中接住一件事，持续推进，直到完成或明确交回用户”**。办公软件可以成为入口和获准数据来源，生活事项继续在小程序 / H5 使用。

最值得先验证的新增场景是：

1. **个人承诺收件箱**：把一条材料通知或工作约定提交给助理，形成有来源、有截止时间的事项，并跟进缺项。
2. **今日行动清单**：在获准日历 / 任务范围内准备当天安排，结合个人事务提示冲突和下一步。
3. **差旅 / 报销材料闭环**：把出行安排、票据和规则整理成清单、缺失项与截止日期，后续继续补充。

以上排序是基于接入门槛、持续执行价值和现有底座复用的产品判断；没有访谈、留存或付费数据，不能称为已验证市场需求。周报、会议摘要作为获客体验可以测试，但本产品的长期价值需要由后续跟进和实际完成证明。

## 2. 证据口径

- **已确认**：在本次可读取的官方说明中存在对应能力，不代表本项目已经有权限。
- **有条件**：能力存在，但依赖应用类型、组织审批、资源授权、用户身份、账号资格或接口合同。
- **待验证**：未取得完整当前官方合同，或需要真实账号测试；不写入首发承诺。
- **产品设计**：以下流程、频率、排序、指标与数据隔离是本项目建议，不是供应商保证。

本次读取企业微信开发者主站部分页面时，浏览器安全策略阻止了该站点操作；没有绕过。企业微信能力主要依据腾讯官方其他产品接入说明和接口目录。飞书部分 API 页面返回空正文，改以飞书官方治理 / 连接器说明与官方 SDK 交叉核对；没有用社区文章替代权限证据。具体协议、账号和限额仍需接入测试。

## 3. 企业微信：入口、推送、内容读取要分开

### 3.1 可确认能力与限制

| 接入方式 | 可确认 / 有条件能力 | 对产品的作用 | 不据此承诺 |
| --- | --- | --- | --- |
| 智能机器人 API 模式 | 腾讯官方接入指南展示长连接、直接对话、群内 @、流式回复 | 用户把具体事项交给 Agent，后台运行后展示结果 | 无差别读取全部群聊、全部个人微信、永久主动推送 |
| 自定义群消息推送 Webhook | 官方说明展示向指定企业群投递消息 | 获准团队提醒或结果通知 | 持有 Webhook 就有读取群聊天内容的能力 |
| 企业应用 | 官方目录有应用消息、部分日历 / 日程操作，受应用与可见范围限制 | 有组织授权时的个人工作提醒与专用计划 | 任意员工安装后即可读取全公司或所有个人日历 |
| 会话内容存档 | 腾讯官方协议确认它是另一个会话数据接口服务 | 后续企业场景的候选数据来源 | 普通机器人权限等于存档权限，或个人授权即可全量接入 |

依据：[智能机器人接入指南](https://cloud.tencent.com/document/product/1831/137051)、[企业群通知](https://cloud.tencent.com/document/product/248/50413)、[企业微信接口目录](https://cloud.tencent.com/document/product/1301/88712)、[会话内容存档服务条款](https://market.cloud.tencent.com/marketplace/protocols/8076)。

腾讯机器人接入指南展示了交互回复和异步处理期限。规划必须区分“回复当前用户请求”和“下个月主动提醒”：前者的临时回复能力不能作为后者的无限通知通道。Connector Profile 单独记录主动发送能力、目标身份、有效窗口、限流与失效策略；长期提醒可改用已获准的应用消息或其他可用渠道。

企微接口目录中的日程列表说明限定为应用创建的日历。这类接口不能用于承诺“登录后汇总用户所有企微日程”；已有日程读取范围作为单独合同测试项。会话存档的具体开通、许可成本、范围及参与人的处理要求，本次未核实完整当前合同，列入企业扩展评估。

### 3.2 推荐的企微第一步

选择 **智能机器人单聊 / 群内明确 @ → 确认事项卡 → 持久执行 → 可用渠道交付**。首个原型只验证文本；图片、文件、引用转发、主动消息和卡片交互逐项测试，不按普通聊天能力推定支持。

用户无需填写模型 Key；机器人创建 / 组织配置可由试点负责人完成。普通消费者没有创建或安装条件时，继续用小程序 / H5 输入同一事项。机器人入口是可选通道，不能成为消费版注册的前提。

外部群、客户群和个人微信与内部群不同，资格、消息及通知合同单独确认。默认不在工作群发布私人生活安排；群内请求默认生成群内可见结果，个人私密结果须走已验证身份的私密入口。

## 4. 飞书：结构化内容更适合逐项扩展

### 4.1 能力与授权矩阵

| 内容 / 入口 | 官方可确认的基础 | 本项目最小接入建议 | 验证条件 |
| --- | --- | --- | --- |
| 单聊 / 群内 @ | 应用机器人可收发获准消息 | 从发给机器人或明确 @ 的消息开始 | 应用可用范围、事件权限、群成员资格与回复目标 |
| 用户身份消息读取 | 官方治理说明列出用户身份消息读取权限 | 后续按用户选定会话、时间窗接入 | 用户 OAuth、具体接口支持、组织限制；不默认全量扫描 |
| 已授权云文档 | 应用 / 用户身份可读对应资源 | 用户选定文档或把应用加入文档协作者 | API 权限与文档资源权限分别满足；有链接不等于可读 |
| 日历 / 日程 / 忙闲 | 官方 Go SDK 提供对应服务；官方说明有用户身份日历变更订阅 | 先只读选定日历或最低必要忙闲 | token 身份、实际可读范围、日历 role、增量 / 周期日程合同 |
| 任务 / 多维表格 | 官方 Go SDK 有 Task v2 服务；官方说明覆盖表记录读写 | 选定清单 / 表，只读状态，写回需固定参数授权 | 资源分享、API 权限、字段、记录、冲突和事件覆盖 |
| 文档 / 审批事件 | 官方事件说明存在具体资源订阅流程 | 有条件订阅允许资源，否则按预算轮询 | 并非只开一个总事件开关就监听所有内容；审批权限另核验 |
| 通知与结果卡 | 应用机器人可向获准对象发送 | 发给已验证本人，群发送另行授权 | 消息受众、身份、频率、格式与回执能力 |

依据：[飞书官方 Agent 权限治理](https://www.feishu.cn/content/article/7615520954977881029)、[云文档连接器](https://www.feishu.cn/content/383321056779)、[多维表格读写说明](https://www.feishu.cn/content/137710114294)、[官方事件订阅说明](https://www.feishu.cn/content/917351528780--3333)、[飞书官方 Go SDK](https://github.com/larksuite/oapi-sdk-go)、[Calendar 服务合同](https://pkg.go.dev/github.com/larksuite/oapi-sdk-go/v3@v3.12.0/service/calendar/v4)、[Task v2 服务合同](https://pkg.go.dev/github.com/larksuite/oapi-sdk-go/v3@v3.12.0/service/task/v2)。

应用身份和用户身份的权限不同：应用身份依赖应用获准范围及资源授权；用户身份依赖用户授权、所选 API 支持和资源权限。组织可能限制应用安装与 OAuth；不能宣传“员工点一下即可连接所有公司内容”。refresh token 维持既有授权，不创造新权限。

飞书官方事件教程说明，云文档、日历、审批可能还需具体资源订阅；教程中的云文档通知订阅有限定条件。因此“能读一篇文档”和“能持续接收它的变化事件”单独测试；不支持事件时只对允许资源做有界轮询。

### 4.2 连接顺序判断

**内容接入优先验证飞书的选定文档 / 日历 / 结构化表；消息入口并行评估企微智能机器人。** 这是本次能力材料支持的工程排序，不是用户规模、转化率或平台市场份额结论。

最终先做哪一个，应由第一批真实用户在哪个平台、能否获得安装授权及创建成功率决定。技术原型可以用团队自己控制的组织验证，不以大多数用户具备管理员权限为假设。

## 5. 十四个具体场景

表中“确认”指需要在产品中完成的确认，未发生任何真实外部动作。L 为低复杂度、M 为中等、H 为高；都是相对工程估计。建议阶段不是全部纳入 MVP。

| ID / 场景 | 用户的一句话 | 需要的内容 | Agent 的持续行为和交付 | 需要确认 / 接入难点 | 建议 |
| --- | --- | --- | --- | --- | --- |
| SC-01 个人承诺收件箱 | “这条通知周五要交材料，帮我盯住。” | 用户提交消息 / 截图；可选机器人消息 | 提取目标、时间、缺项和来源；用户确认后跟进、提醒，补齐后关闭 | 不把群内随口表达自动认定为所有人的承诺；办公资料处理需获准 | P0 输入复用；办公入口试点，L–M |
| SC-02 今日行动与冲突 | “每天早上告诉我今天要办什么。” | 用户保存事项；可选获准日历 / 任务、最低必要忙闲 | 输出 3–5 个行动项、冲突和准备材料；改期后更新 | 工作详情与私人计划分域；不未经许可把生活内容写回公司日历 | 先 P0 个人事项；办公读取试点，M |

| SC-04 会后个人跟进 | “纪要里我答应的事，帮我持续跟进。” | 用户上传纪要 / 已授权会议文档 | 建候选承诺，确认本人负责项，检查进度与到期，准备追问草稿 | 不替他人确认任务；自动向同事催办需逐次批准 | 先上传纪要验证；连接器后加，M |
| SC-05 差旅与报销材料 | “这次出差结束后别忘了报销，材料缺什么告诉我。” | 用户提供行程、票据、经允许的规则文档 | 建出发 / 返回 / 报销阶段清单；票据到齐后核对缺项，提醒截止，导出草稿 | 金额与日期核对；不承诺报销系统已提交或审批通过 | 首批新增场景，M |
| SC-06 周报与成果记录 | “周五给我一份有依据的本周总结。” | 用户日志；可选授权任务 / 表格 / 文档 | 周内收集已确认成果、待解决项，生成带链接草稿，用户修改后归档 | 不把他人成果认领给自己；外发先确认，别只做一次摘要 | 需求访谈 / 辅助入口，M |
| SC-07 自由职业交付跟进 | “这三个客户的交付和尾款事项帮我记住。” | 用户明确提供的里程碑 / 资料；可选本人获准的表 | 检查待交文件和约定日期，生成发信 / 跟进草稿，收到确认后更新状态 | 不默认读取全部客户聊天；不能将提醒等同收款成功 | 小规模独立试验，M–H |
| SC-08 外出方案持续更新 | “周末去杭州，天气变了提醒我换安排。” | 用户日期 / 城市 / 偏好、公开天气和已提供订单 | 分阶段准备清单；获准检查天气等变化，仅达到条件才提醒 | 只读检查属 P1；订单来自用户或 verified connector，预订另确认 | 保留主场景，P0 准备 / P1 检查，M |
| SC-09 家居到期与维护 | “房租续签、宽带续费、滤芯更换，帮我统一管理。” | 用户日期、账单、商品维护说明 | 管理多个长期事项，提前提醒、展示材料和比对旧安排 | 读取规则与用户提供事实；不自动续约、付款或给出法律结论 | 生活扩展优先，L |
| SC-10 售后与退换准备 | “这次退货什么时候寄出，要留哪些东西？” | 用户订单 / 售后页面截图、已告知时限 | 保存包裹 / 凭证 / 日期清单，提醒寄出，用户提供进度后继续 | 不把截图当已申请退款或已到账；具体店铺规则待核实 | 小规模生活试验，L–M |
| SC-11 学习与考试计划 | “八周后考试，每周帮我调整准备计划。” | 用户课程表、学习材料与反馈 | 有界每周复盘、安排练习和复习，调整未完成事项 | 学习结果需实际反馈；不全量抓取课程平台或承诺成绩 | 成人用户试验，M |
| SC-12 求职个人管家 | “面试时间、公司资料、投递进度帮我整理。” | 用户邀请邮件 / 截图、JD、本人简历 | 管理材料和面试日期、准备清单，面试后记录个人反馈与下一步 | 不默认自动投递或回复；不以 Agent 决定他人的招聘结果 | 独立成人场景试验，M |
| SC-13 个人资料与收藏转行动 | “这些活动链接里，哪些需要我报名或准备？” | 用户保存的公开链接、文件、截图 | 识别日期和行动候选；确认后转事项，旧资料变化按授权检查 | 链接访问受规则与权限限制；不能自动抓取所有私人收藏 | 与 SC-01 共用底座，L–M |
| SC-14 家庭成人协作 | “我和伴侣一起安排搬家，谁负责哪件事？” | 每位成人分别授权的事项和文件 | 形成分工候选，共同确认时间，分别通知获准成员 | 跨用户共享、撤回和受众复杂；不能单人授权采集全家数据 | P2，H |

天气检查可使用获准天气 API；例如和风天气官方提供每日预报合同。型号、区域、次数、更新频率和商业使用条件在接入时核验，天气变化只是建议依据。[官方天气预报 API](https://dev.qweather.com/docs/api/weather/weather-daily-forecast/)

SC-09 / 10 / 11 / 12 / 13 的首个闭环只需用户提供资料和现有事项底座，不依赖“读取所有 App”。本次未验证各购物、银行、招聘或课程平台的私人账户通用读取接口，不将其作为上述场景的默认条件。医疗解释、投资建议、自动支付与抢票不列为本轮新增主线。

## 6. 三个优先场景的具体流程

### 6.1 个人承诺收件箱：最适合共用核心底座

1. 用户在 H5 上传通知，或在已安装的飞书 / 企微机器人入口明确提交这件事。
2. 助理保留原消息引用、可见范围和来源，不读取同会话其他内容来猜测授权。
3. 提取“我的目标 / 日期 / 准备项 / 需要他人决定”的候选。日期、责任人、重要字段有冲突就确认。
4. 展示事项卡，用户确认范围、保存和提醒渠道。办公资料不得未经组织允许复制到个人模型或其他通道。
5. 创建 Matter 与必要 Reminder；缺材料时 WAITING，用户补充后从相同事项继续。
6. 到期提醒走确定性通知。用户改期、完成或撤销后，旧版本停止未提交动作。
7. 交付清单 / 文件，用户确认完成；“整理好了”和“已经向公司提交”分开显示。

验证指标：从输入到确认的时间、关键字段准确率、用户主动补充率、后续完成率、每个有效事项成本；所有值待测。

### 6.2 今日行动清单：工作与生活如何共存

1. 用户先选择个人事项和允许读取的工作来源，分别设置受众与用途。
2. 工作环境只能在其获准执行 / 模型范围处理。若组织允许输出忙闲，只传最低必要时间块；若禁止外发，则清单留在办公环境，个人界面仅显示获准提示或用户自行录入的安排。
3. 每天固定一次准备当天行动清单，日历改变或用户补充后按预算有界更新，不每分钟全量调用模型。
4. 展示今天必须做的事、冲突、会前准备与缺失信息；每项可回到来源。
5. 用户选“调整 / 稍后 / 完成”；修改外部日历先展示具体目标和影响，收件人或群组动作不能自动带入。
6. 渠道无授权 / 不支持长期发送时，保存站内清单并提示，不伪造晨间推送已送达。

价值假设：用户是否愿意每天查看并处理真实事项。若只是阅读摘要而不推动事务，降低它作为主入口的优先级。

### 6.3 差旅与报销材料：跨阶段事项

1. 用户提交出行日期、城市和已购订单截图；系统不自行读取个人账户全量订单。
2. 保存阶段：出发前准备、返回后整理、材料提交截止；识别不确定日期需确认。
3. 有组织许可时读取指定报销规则，附版本 / 核验时间；无许可由用户提供可处理材料。
4. 用户陆续上传票据，系统标记缺项、重复、日期 / 金额待核实，生成材料索引与草稿。
5. 到期前通知本人；用户完成真实提交后提供回执或手动确认，平台据此更新状态。
6. 受支持审批连接器未来可核对提交进度，但申请、催办、报销通过 / 到账各有独立证据和授权。

适合首批验证的原因：资料、日期、等待、补充与交付共用已有能力，且完成条件比泛泛“提高效率”更容易核对。这是分析判断，仍需测需求频率和用户持续使用。

## 7. 场景排序与产品边界

| 组别 | 场景 | 排序理由 | 不确定性 |
| --- | --- | --- | --- |
| 首批核心 | SC-01 个人承诺、SC-08 外出准备 | 覆盖当前主线，输入简单、闭环清楚 | 用户是否愿意持续提交资料和处理事项 |
| 首批扩展验证 | SC-02 今日行动、SC-05 差旅材料、SC-09 家居到期 | 有长期状态与明确提醒价值，可先手动输入 | 日历权限、场景频率、离线触达 |
| 功能补充 | SC-03 / 04 会前会后、SC-06 周报、SC-13 收藏 | 复用资料与任务能力 | 与现有办公产品差异、是否只消费摘要 |
| 独立实验 | SC-07 自由职业、SC-10 售后、SC-11 学习、SC-12 求职 | 目标明确，可选择小人群验证 | 留存周期、效果评价、垂类需求 |
| 后续平台化 | SC-14 家庭协作、企业全量存档 / CRM | 涉及多人、多组织与更多治理 | 权限、实施与成本显著增加 |

暂不把全公司知识问答、员工监控、企业 CRM、考勤审批、销售自动群发同时纳入消费版。它们的购买者、权限、实施和售后与个人助理不同；若出现企业订单再单独定义企业产品。

办公群里的结果只发给有权的受众。生活偏好、私人求职、家庭资料不因用户同在一个办公平台就进入公司的问答或群摘要。

## 8. 小规模验证计划

### 8.1 先证明权限与渠道

用自有或明确允许试点的组织和测试身份，不需要读取真实员工历史。两个平台各验证：创建 / 安装、私聊、群内 @、接收去重、确认卡、异步完成、长期提醒、撤销 / 退出组织、格式与限流。企微还测回复窗口和重连；飞书再逐项测文档、日历、任务 / 表格。

产出能力清单：SUPPORTED / CONDITIONAL / UNSUPPORTED / UNKNOWN；未知或失败功能在 UI 不出现可执行按钮。OAuth、密钥、refresh token 和机器人 Webhook 只进加密 Credential Store，不让用户贴进群聊。

### 8.2 再验证实际事务

建议在既有 20–50 名受邀用户中选择两个各 5–10 人的办公入口试点；人数是计划，不是已经招募的样本。不能要求每位用户都是管理员；记录安装失败和权限拿不到的用户，避免只看能接入的人。

先复用生活事项基线，办公试点额外记录：

- 创建 / 安装完成率，以及管理员依赖导致的放弃。
- 用户每周真实提交事项数、确认率、修改率和完成率。
- 重要日期 / 责任人错误、重复发送和来源权限失效。
- “主动提醒有用 / 多余 / 打扰”的反馈，通知是否可核实。
- 每个完成事项的模型、资料读取、连接维护与通知成本。
- 用户是否主动再次交给助理一个事项，而非只体验一次摘要。

可用以下 **待验证门槛** 决定继续：日期 / 权限验收无静默错误；至少一半试点用户第二周主动提交或处理真实事项；相较手动输入，连接器没有显著增加首次使用负担。小样本需报告人数与案例，不能推导总体市场比例。

### 8.3 阶段含义

办公连接器使用 **C0 / C1 / C2** 表示本轮试点能力，独立于原 P0 / P1，不自动推迟生活版：

| 阶段 | 范围 | 准入 |
| --- | --- | --- |
| C0 入口试点 | 单聊 / 明确 @，用户提交内容，确认事项与可用交付 | P0 基础事项、隔离和通知已可靠；组织允许 |
| C1 内容试点 | 选定飞书文档 / 日历 / 表，或企微实际合同允许的资源 | 具体读取权限、当前 ACL、用途与成本通过 |
| C2 后续动作 | 外部日程 / 任务写回、指定变化订阅、受支持催办 | 固定参数审批、副作用幂等 / 核对和撤销验证 |

会话全量存档、企业统一管理和家庭共享不是 C0–C2 自动包含项。是否加入、在哪一期以及工期由验证结果决定，原 P1 云端电脑 / 语音等估算不包含办公连接器额外范围。

## 9. 对工程底座的增量要求

不用改变 Go + Temporal 主架构；增加 ConnectorProfile、IntegrationInstallation、IdentityBinding、DataGrant、SourceBinding 与来源安全域。消息适配、内容读取、结果通知是三个合同，不能用一个“已连接”开关概括。

最关键的设计是：一个办公机器人可以服务多个用户，但不能共享他们的私密 Context 或 Memory。执行至少检查 provider / tenant / app / actor / resource / recipient / purpose / current grant；来源 ACL 缩小时停止后续读取与投递，清除相应缓存、摘要与索引。

企业内容默认留在其允许的处理边界；从工作日程提取的忙闲、标题或待办也可能仍受来源约束，不能因成为摘要就自动认为可外发。技术细节与新增验收见配套架构 / PRD。

## 10. 调研产物与未完成事项

本轮完成公开能力核对、十四个场景、三个详细流程、连接器分级、试点与数据边界设计。没有安装应用、接入账号、发送消息、获取真实工作内容或进行市场规模统计。

待真实原型核验：平台 / 账号安装资格、每个 API 的 token 与最新权限、聊天历史可用范围、媒体文件、卡片回调、消息窗口、日历授权、事件覆盖、限流、价格、撤销和通知回执。

后续用户访谈应围绕真实最近一周事项及实际资料来源，观察用户是否愿意提供内容、完成授权和处理结果，不只询问“你想不想要一个 AI 助理”。
