# Agent OS / Agent Cloud Runtime 产品需求文档

版本：v0.1 · 日期：2026-10-04 · 状态：首版设计稿，可据此拆分开发任务

项目暂称 **Orbit Runtime**。这是工作名称，后续可以更换。配套技术设计见 [架构文档](./ARCHITECTURE.md)。

## 1. 产品定位与设计结论

为个人开发者、研究人员和小团队提供一个可自托管的常驻 Agent 平台。用户为 Agent 指定长期职责、模型、数据来源、工具、授权范围和预算；平台在用户离开页面后继续执行，在定时或事件触发时开展新工作，保存执行记录和结果，并在需要用户决定时等待。

**首版产品承诺：一个有持续职责的 Agent，能够在后台可靠执行、跨次运行保留上下文、在明确权限内行动，并让用户看见发生了什么。**

“Agent OS”在本项目中指 Agent 的任务、状态、工具、模型、权限、记忆和执行资源管理层，不涉及开发操作系统内核。“Cloud Runtime”表示服务端后台执行；允许部署在个人服务器或私有环境。

产品核心链路：

```text
长期职责 → 手动 / 定时 / 事件触发 → 持久执行
       → 模型与工具 → 审批 / 等待 → 结果与记忆 → 下一次运行
```

### 1.1 与 OpenAI dots 的参考关系

截至本稿日期，官方文档描述 dots 可以持续承担职责，在对话间继续工作，按时间或支持的事件开展工作，并呈现后台任务供用户检查。本文参考这些产品体验。[来源：Tasks and memory](https://learn.chatgpt.com/docs/dots/tasks-and-memory)

dots 官方也描述了连接应用、云端计算环境和 Activity 中的进度及结果查看能力。[来源：Get started with your dot](https://learn.chatgpt.com/docs/dots/getting-started)

影响账户或分享信息的操作需要结合指令、权限及审批检查；起草内容与发送内容存在不同授权范围。[来源：Control your dot](https://learn.chatgpt.com/docs/dots/controls)

上述是公开产品行为。**本文的 Temporal、数据库结构、模型网关、权限引擎和部署方案均为本项目的独立设计，不代表 dots 的内部实现。**

## 2. 问题、目标用户与价值

### 2.1 要解决的问题

1. 用户反复提供相同职责、数据来源和偏好，每次工作都从新对话开始。
2. 用户关闭页面或执行进程崩溃后，长任务无法可靠继续。
3. 定期检查与外部事件分散在脚本、聊天机器人和自动化工具中，缺少统一进度。
4. 模型被绑定到 Agent，更换模型需要重写业务逻辑。
5. 自动化写操作缺少明确授权、可审阅草稿和可追踪的执行结果。
6. 用户无法判断 Agent 是否完成了工作、花费多少，以及是否真的交付到目标位置。

### 2.2 用户与场景优先级

| 用户 | 主要职责场景 | 当前痛点 | 首版提供的价值 |
| --- | --- | --- | --- |
| 开发者 / 开源维护者 | 关注指定仓库 Issue，整理新问题和建议 | 信息重复、需要定期查看 | 有变化才提示，评论先审后发 |
| 研究人员 / 知识工作者 | 跟踪 RSS 和指定公开网页，整理主题报告 | 周期性搜集与去重耗时 | 保留已读记录，报告有来源链接 |
| 技术型个人用户 | 用自己的模型和 API 运行助手 | 供应商限制、配置分散 | 模型连接和运行规则统一管理 |

企业行政、销售全流程、邮件自动发送、生产基础设施运维不作为首版验证场景。

### 2.3 产品目标

| 目标 | 衡量方式 | 内测目标 |
| --- | --- | --- |
| 快速获得首个结果 | 从开始配置到首次有效 Run，排除用户寻找 Key 的时间 | 受邀用户中位数 ≤ 15 分钟 |
| 产生持续价值 | 激活用户在两周内使用至少一个持续职责 ≥ 3 次 | ≥ 50% |
| 可恢复 | 在明确故障注入点终止 Worker 后恢复运行 | 验收用例全部通过 |
| 用户保有控制权 | 写操作受权限约束，审批内容与实际动作一致 | 约定验收集内无越权动作 |
| 交付可核验 | 报告、评论具有可访问产物或外部回执 | 成功用例全部可核验 |
| 花费可解释 | 模型请求显示供应商、Token、计费状态和估算依据 | 所有模型请求都有账目状态 |

“有效 Run”指用户确认结果有用或通过场景验收；仅流程结束不能证明结果正确。

## 3. 范围与版本分层

P0 是首版发布必须具备的能力；P1 是通过首版场景验证后的下一阶段；P2 是后续规模化能力。

| 能力 | P0：MVP | P1 | P2 |
| --- | --- | --- | --- |
| Agent 管理 | 创建、编辑、版本、启停，绑定 Workspace | 模板导入导出、共享 | 模板市场和组织治理 |
| 模型接入 | OpenAI、Anthropic 原生适配；通过验证的 OpenAI-compatible 端点 | Gemini 原生、Ollama / 私有网络连接器 | 企业网关、复杂质量路由 |
| 路由 | 默认模型 + 用户配置的有序回退，能力和数据边界过滤 | 按任务阶段选模型 | 基于评测的质量 / 成本优化 |
| 执行 | 单 Agent 有限步循环、恢复、取消、暂停、预算 | Child Run、有向任务依赖 | 多 Agent 编排 |
| 触发 | 手动、一次性、周期计划、签名 Webhook | 更多应用事件、条件触发 | 复杂事件匹配 |
| 工具 | 内置读取 / 文件工具、GitHub 读与评论、管理员审核的远程 MCP | OpenAPI 导入、更多连接器 | 插件市场 |
| 权限 | ALLOW / ASK / DENY，参数级审批、撤销、审计 | 授权有效期与更多条件 | 团队多级审批 |
| 记忆 | 执行摘要、结构化偏好、已处理对象；查看、编辑、删除 | pgvector 检索和候选记忆提取 | 关系记忆和跨任务知识体系 |
| 文件 | Markdown / JSON / CSV 产物和安全下载 | 隔离代码执行、PDF 等产物 | 长期计算环境 |
| 浏览器 | 受控 HTTP 获取公开 HTML / RSS | Playwright 隔离浏览器 | 桌面计算机控制 |
| 可观测性 | Run 时间线、步骤、错误、账目、审计 | 评测工作台 | 企业级可观测平台 |
| 消息 | 站内提醒 | 用户授权的邮件 / 飞书 / Slack 通知 | 多渠道会话 |
| 多用户 | 邀请制账户、单 Owner Workspace 隔离 | Workspace 成员和简单角色 | SSO、组织策略 |

首版不做支付结算、模型训练、通用桌面客户端、移动客户端、任意远程程序安装、云资源删除、自动合并 PR，以及无限循环的“自主探索”。

## 4. 核心概念与产品模型

| 概念 | 定义 | 示例 |
| --- | --- | --- |
| Workspace | 数据、授权和配置的隔离空间 | 个人研究、开源项目 A |
| Agent Definition | 可版本化的行为模板 | “仓库观察员”v3 |
| Agent Instance | Workspace 中长期存在的具体 Agent | 我的仓库观察员 |
| Task | 一次目标或持续职责 | 每天检查指定仓库的新 Issue |
| Run | 某次实际执行 | 2026-10-04 09:00 的检查 |
| Step | 一个逻辑执行步骤 | 获取 Issue、模型归纳、提交评论 |
| Attempt | 同一 Step 的一次实际尝试 | 第一次超时、第二次成功 |
| Trigger | 创建执行的规则 | 每天 09:00、Issue Webhook |
| Approval | 对具体动作的决策记录 | 向 Issue #42 发布这段评论 |
| Memory | 跨 Run 使用的知识或记录 | 不重复报告已处理 Issue |
| Artifact | 可查看或下载的结果文件 | issues-2026-10-04.md |
| Connection | 对模型或外部服务的接入配置 | 用户的模型端点、GitHub 凭据引用 |

关系为 `Workspace → Agent Instance → Task → Run → Step → Attempt`。一个 Task 可产生多个 Run；一次失败后的“重新运行”创建新 Run 并关联原 Run。“恢复”继续同一个未结束的 Run。

**常驻的对象是职责、配置和状态。Agent 空闲时等待事件，不为每个 Agent 保持一个持续占用 CPU 的进程。**

### 4.1 状态定义

Agent 配置状态：`ENABLED / DISABLED / ARCHIVED`。卡片上的“运行中 / 需要处理 / 等待下次运行”来自当前 Run 和 Trigger 的汇总。

Task 状态：`ACTIVE / PAUSED / COMPLETED / ARCHIVED`。一次性任务达成后完成；持续职责在某次 Run 完成后仍然 ACTIVE。

Run 状态：

| 状态 | 用户含义 | 是否占用执行额度 |
| --- | --- | --- |
| QUEUED | 已接收，等待执行 | 否 |
| RUNNING | 正在执行步骤 | 是 |
| WAITING | 等待用户、审批、事件或定时恢复 | 否 |
| PAUSED | 用户暂停当前执行 | 否 |
| CANCELLING | 正在停止，并检查已开始的动作 | 可能短暂占用 |
| SUCCEEDED | 已生成所需结果，并满足本 Run 的交付约定 | 否 |
| FAILED | 执行失败，保留已有结果 | 否 |
| CANCELLED | 当前运行已停止 | 否 |

WAITING 带原因：`APPROVAL / USER_INPUT / EVENT / TIMER / CREDENTIAL / BUDGET / RECONCILIATION`。RECONCILIATION 表示外部动作的结果需要核对，不能直接视为失败重试。

Run 另有 `delivery_status`：`NOT_REQUIRED / PENDING / DELIVERED / UNKNOWN / FAILED`。需要交付外部评论的 Run 不能在结果 UNKNOWN 时标为 SUCCEEDED；若职责只要求起草，保存草稿即可满足交付。

## 5. 两个首版闭环场景

### 5.1 主题资料观察员

用户指定最多 10 个公开 RSS / HTML 地址，描述关注主题，选择模型，设置每天 09:00（Asia/Shanghai）检查。用户可选择“有新内容才提醒”或“每次生成摘要”。

流程：

1. 创建 Agent 和持续 Task，展示职责、来源、预算和下一次时间。
2. 用户立即试跑；平台获取资料、按来源标识去重、归纳相关内容。
3. 报告区分新增内容、来源事实和 Agent 的分析；每个引用链接可追溯到本次抓取。
4. 保存 Markdown 产物和已处理记录；仅在结果持久化后推进处理游标。
5. 用户关闭页面，下一次计划仍在服务端启动。
6. 无新增且无需处理时不发站内提醒，但 Run 记录可查看。

验收：连续三次运行不重复报告已处理条目；模拟中途崩溃后继续；报告中的来源链接均属于实际读取的来源，不能凭空生成引用。失效来源显示失败，不把“未读取”描述为“没有新内容”。

### 5.2 GitHub Issue 观察员

用户连接具有最小必要权限的 GitHub 凭据，允许访问一个指定仓库，并配置关注标签。新 Issue 通过 Webhook 或每日定时触发。

流程：

1. 读取 Issue 内容与相关公开或已授权仓库材料。
2. 生成问题摘要、潜在原因、建议排查步骤，以及可选的评论草稿。
3. 若 Task 只要求建议，保存报告后完成。
4. 若 Task 要求评论，展示仓库、Issue、完整评论内容和发送身份，等待审批。
5. 用户批准具体草稿，平台重新校验权限与内容一致性后发送，保存外部评论 URL。
6. 若拒绝，保存草稿并结束为用户拒绝的结果；若用户改稿，生成新的审批。
7. 如果发送结果不明，提示“需要核对是否已发布”，通过外部标识查询或交给用户确认。

首版仅提供 `github.list_issues / github.get_issue / github.get_repository_file / github.create_comment` 等审核工具；自动修改代码、创建 PR、合并和删除资源进入后续版本。

验收：同一 Webhook 重放只创建一个有效 Run；未批准不发送；批准后正文或目标变化必须重新审批；模拟“远端成功、本地未收到回执”时不盲目发送第二次。

## 6. 功能需求与验收标准

### FR-01：账户与 Workspace（P0）

提供邀请制登录、退出、个人 Workspace 与项目 Workspace。首版角色仅 Owner；所有 Agent、连接、任务、记忆、产物和事件都属于一个 Workspace。

验收：A 用户不能通过猜测 ID、下载地址、事件订阅或后台任务访问 B 用户数据；切换 Workspace 后不继承原空间的模型凭据和记忆。

### FR-02：模型连接与能力校验（P0）

连接表单包含 Provider、Base URL、凭据、模型标识、能力配置及价格信息。原生 Provider 使用官方端点模板；OpenAI-compatible 自定义端点需管理员允许的网络范围。

提供“验证连接”操作，说明会发送测试请求并可能产生小额供应商费用。模型列表接口不可用时允许填写模型标识。连接状态区分未验证、可用、异常、凭据失效和已禁用。

能力记录采用 `SUPPORTED / UNSUPPORTED / UNKNOWN`，记录声明或测试的来源和日期。工具调用、上下文长度等硬要求不满足时，禁止启动需要该能力的 Task。模型列表返回结果不能证明能力。

验收：OpenAI、Anthropic、至少一个通过兼容测试的 OpenAI-compatible 端点完成同一工具调用场景；缺少工具调用的模型只能用于纯文本任务或被拒绝；不承诺所有兼容端点行为相同。

连接测试和任何回退都受数据发送范围约束；用户须明确选择可接收该 Workspace 数据的供应商。云端 localhost 不指向用户电脑，首版不通过公网 API 自动访问用户本地模型。

### FR-03：Agent 创建与版本（P0）

创建流程：选择模板 → 名称与职责 → 默认模型及回退 → 工具和来源 → 权限 → 预算 → 试跑。

已发布的 Definition 版本不可变。修改后创建新版本，新 Run 默认使用新版本；正在运行的 Run 保留启动时版本。凭据撤销、Agent 禁用、管理员限制仍立即约束后续动作。

验收：查看任一历史 Run 能知道使用哪个 Agent 版本、模型策略和工具版本；编辑 Agent 不改变历史记录。

### FR-04：创建 Task 与持续职责（P0）

用户可选择“一次任务”或“持续职责”，指定目标、来源、完成条件、结果位置和通知规则。自然语言可生成配置草稿；首版以可审阅的表单为保存依据。

“每天帮我看看”必须补充或采用界面明确展示的时间、时区与通知默认值；未保存计划只会试跑，不默默创建周期任务。一个 Agent 可以有多个 Task，每个 Task 独立启停。

验收：任务卡显示目标、触发方式、下一次运行和最后结果；持续职责一次完成后仍可触发；试跑与保存周期计划行为明确。

### FR-05：后台执行与恢复（P0）

前端启动后立即获得 Run ID，可关闭页面。平台记录计划摘要、工具调用、模型输出、结果和错误。恢复从已提交的步骤结果继续，不重复完成的本地步骤。

模型请求重试可能带来额外计费，必须显示 Attempt；外部写操作结果不明时转为核对等待。Run 等待期间释放模型并发和执行资源，等待本身不持续请求模型。

验收：分别在模型请求、读取工具、保存产物、审批等待阶段重启 Worker，Run 可正确继续；不宣称第三方副作用具有全局 exactly-once 保证。

### FR-06：时间与事件触发（P0）

支持手动、未来一次性运行、Cron / 简单周期和签名 Webhook。时间界面展示 IANA 时区与接下来三次运行，默认 Asia/Shanghai；一次性输入转换为 UTC 保存。

周期任务默认不重叠；上一 Run 仍在运行、等待或暂停时，新触发记为“跳过：已有运行”。错过运行默认不补齐历史序列；恢复时允许在约定窗口内执行最新一次，默认窗口 10 分钟，多次候选合并为一次并记录。

上述跳过规则针对周期触发。手动启动遇到已有 Run 时引导打开原运行；Webhook 则保留待处理事件，当前 Run 结束后合并处理。每 Task 初始最多保留 1,000 个待处理事件，达到上限时拒绝新的接收并告警，不在已接收后丢弃事件。

计划暂停只阻止新触发，不停止当前 Run。Task 暂停阻止新 Run；已有 Run 的处理选项单独显示。删除或禁用触发应立即影响后续接入，不能只靠界面隐藏。

事件配置指定来源、签名校验、匹配条件和 Task。事件输入属于数据，不能更改工具权限；首版不提供任意表达式执行。

验收：重复事件去重；时区预览正确；同一 Task 不并发重复运行；计划修改后旧版本不再产生有效新 Run；未通过签名校验的 Webhook 不进入执行。

### FR-07：统一工具与连接（P0）

用户从审核后的工具目录选择工具。每项展示作用、输入、读写属性、目标范围、凭据连接、审批策略和健康状态。远程 MCP 仅作为一种工具协议。

首版 MCP 服务器由管理员接入和审核，工具清单与 schema 版本固定；工具自称只读不能获得自动授权。新工具或 schema 变化需重新审核。

读取工具受资源范围与数据外发策略约束；写工具默认 ASK；删除、支付、权限更改默认 DENY。报告文件写入自己的受控工作区可 ALLOW。

验收：模型只可看到并调用 Run 的工具白名单；伪造未知工具名、越界参数和改变 schema 均被拒绝；MCP 断开显示明确连接错误。

### FR-08：审批与授权（P0）

审批卡必须显示动作、外部服务、目标对象、完整将执行内容、发送身份、可能影响、费用提示和过期时间。批准 / 拒绝按钮对应确定的调用参数，不只批准一句自然语言意图。

默认审批有效期 24 小时；批准为一次性授权。用户可授权范围明确的未来读取行为；首版外部评论写入逐次审批，不做自动泛化授权。

执行前重新检查当前权限、目标与凭据。参数或目标变化、审批过期、权限撤销都使原审批失效。用户批准的草稿必须按原样执行，不允许再由模型润色后直接发送。

验收：重复点击批准不能重复执行；未授权用户不能决定；审批期间服务重启后仍可决定；拒绝可结束或让 Agent 生成新方案，拒绝的动作本身不执行。

### FR-09：记忆（P0）

记忆分为当前 Run 工作上下文、历史执行摘要、用户确认的偏好，以及来源处理游标。文件本体作为 Artifact 保存，不把向量数据库当作全部记忆。

工作区知识默认隔离；Agent 专属历史与用户明确共享的 Workspace 知识分别管理。用户可看来源、更新时间，编辑、删除或关闭长期记忆。P0 的自动摘要限于本平台已发生的事实；从文本提取偏好作为候选，未经确认不提升为用户指令。

删除或撤回后，后续模型调用不可再次加载该记忆；已送往供应商的历史请求无法撤回，界面须准确表达删除范围。提示注入内容不能成为可改变权限的记忆。

验收：连续运行按已处理对象去重；纠正后的偏好在后续 Run 生效；跨 Workspace 无检索混入；关闭记忆仍保留必要执行账本与审批审计。

### FR-10：上下文组装（P0）

按模型能力为目标、当前状态、近期消息、工具描述、相关记忆和来源内容分配 Token 预算。过长工具结果生成摘要并保留原始文件引用；禁止默默截断关键约束。

外部网页、Issue 和工具结果带来源标签，以数据形式进入上下文。模型不保存隐藏推理过程；对用户显示可核验的操作摘要、理由说明与证据。

验收：超出上下文时出现清晰的降级或错误；必要权限与任务约束不被删除；模型切换后上下文被重新适配。

### FR-11：产物与交付（P0）

每个 Run 可产生 Markdown、JSON、CSV 等产物。记录名称、类型、大小、创建时间、来源 Run 和内容哈希；支持预览和鉴权下载。

Agent 生成文件与实际发送到外部位置是独立事件。发送评论必须有外部 ID / URL 或已核对的证据。预览 HTML 或 Markdown 时过滤危险内容；文件下载链接短期有效。

验收：用户能从时间线打开产物；文件内容在重试中不会错绑定到其他 Run；外部发送失败不会只显示“已完成”。

### FR-12：预算与终止（P0）

默认每 Run 上限：30 个逻辑执行 Step、总计 60 个模型 / 工具 Attempt、15 分钟活跃执行时间、7 天墙钟生命周期。等待审批默认 24 小时；单个模型请求默认 120 秒，普通 HTTP 工具 30 秒。

美元计价连接的 Run 费用预算默认 1 USD，Workspace 日预算默认 5 USD，均可修改；其他币种需独立配置预算，不自动做跨币种汇率换算。计费单价未知时显示未知，不当作零；严格费用控制模式禁止调用，用户填入估算上界后才可执行。BYOK 账目是估算及用量记录，不是供应商最终账单。

费用预算不足时进入 WAITING(BUDGET)，停止启动新请求。步数、Attempt 或活跃执行时间超限时以 LIMIT_EXCEEDED 原因结束为 FAILED；墙钟生命周期到期同样结束。增加费用额度只改变费用预算，不自动扩展权限；7 天上限和审批期限仍适用。费用判断覆盖重试、回退与后续版本的子任务；取消时已有请求仍可能产生费用。平台预算限制新请求的启动，不代替供应商最终账单或账户硬支出限制。

用户可暂停当前 Run、继续当前 Run、取消当前 Run、暂停 Task、禁用 Agent。禁用 Agent 拒绝新运行并向现有运行发出取消请求；已经开始的外部动作仍需检查结果。

验收：并发请求不能超卖已预留预算；超限不继续无穷重试；取消后无新业务动作；界面准确显示已完成且无法撤销的副作用。

### FR-13：运行时间线与通知（P0）

时间线展示状态、工具名称、可披露参数、模型与供应商、时间、Token、估算费用、错误原因、审批及产物。日志对秘密和敏感输入脱敏。

站内提醒类别：有价值的新结果、审批或补充信息、失败和凭据失效。无变化的检查只留运行记录。重复失败可合并通知；打开提醒可定位原 Run。

验收：断线重连可补齐持久事件；事件不存在跨 Workspace 泄漏；日志和前端 API 不返回完整 Key；未知计费与未知交付都有明确标记。

## 7. 信息架构与页面设计

```text
Workspace 切换
├── 总览：运行中、待处理、下次运行、最近结果、今日用量
├── 我的 Agents
│   └── Agent 详情
│       ├── 职责与 Tasks
│       ├── 活动与 Runs
│       ├── 记忆
│       ├── 文件
│       └── 配置：模型 / 工具 / 权限 / 预算 / 版本
├── 任务：一次任务、持续职责、触发计划
├── 待处理：审批、补充信息、异常核对
├── 连接：模型连接、GitHub、审核后的 MCP
└── 设置：账户、凭据、数据保留、审计
```

### 7.1 关键页面要求

| 页面 | 首要信息 | 关键操作 |
| --- | --- | --- |
| 总览 | 哪些工作需要我决定，最近带来什么结果 | 处理审批、打开报告、创建 Agent |
| Agent 列表 | 名称、职责、当前状态、下一次运行、异常 | 启停、进入详情 |
| Agent 详情 | 职责、结果、执行状态、可用能力 | 新任务、试跑、配置版本 |
| Run 详情 | 目标、状态、步骤、费用、产物、交付回执 | 暂停、取消、继续、重新运行 |
| 待处理 | 待决定的具体动作和完整内容 | 批准、拒绝、修改草稿 |
| 计划配置 | 任务、时区、未来三次运行、重叠和补跑规则 | 保存、暂停、删除 |
| 模型连接 | 数据会发往哪里、能力、价格、验证状态 | 验证、更换凭据、禁用 |
| 记忆 | 内容、来源、作用范围、时间 | 编辑、删除、关闭 |

Run 详情可以提供对话区补充信息，但结果、审批、状态和产物具有独立卡片。纯工程内部 ID、Temporal 状态和底层堆栈放在可展开诊断区，不进入用户主要工作流。

### 7.2 空状态与失败状态

新用户总览给出“创建资料观察员”和“创建仓库观察员”入口。模型未连接时引导配置并验证；没有可用工具时清楚说明当前可做的纯文本工作。

典型失败文案分别说明“读取来源失败”“模型额度不足”“需要重新连接”“已等待审批”“无法确认评论是否发送”。失败页保留已完成工作并提供对应处理入口，不只显示统一的任务失败。

## 8. 非功能需求

| 类别 | MVP 目标与测量边界 |
| --- | --- |
| 接收性能 | 5 并发、正常依赖下，创建 Run API P95 ≤ 1 秒；不包括模型执行 |
| 调度延迟 | 正常服务状态下，持久接收到应运行事件至进入可执行队列 P95 ≤ 10 秒；不包含资源排队 |
| UI 状态延迟 | 持久业务事件到在线界面 P95 ≤ 2 秒 |
| 并发 | 初始全局 5 个活跃 Run、每 Workspace 2 个、每 Task 1 个；等待不计入活跃槽 |
| 故障恢复 | Worker 替换后，在测试中 60 秒内重新开始可恢复步骤；依赖长时间不可用另计 |
| 安全 | 所有对象、下载、事件流和异步任务进行 Workspace 授权；外部写入统一走执行策略 |
| 数据可靠性 | API 返回已接收前，Run / 事件与待发送命令已持久化；跨系统一致性经重试和核对实现 |
| 保留策略 | 执行内容默认 30 天、产物和记忆默认 90 天、最小审计元数据默认 180 天，均可配置 |
| 可运维性 | 开发环境一套 Compose 启动；服务有健康检查、备份恢复步骤和故障诊断 |
| 可迁移性 | Agent 配置、Task 配置、结果和记忆可导出；原始凭据不导出 |

不对首版承诺公共 SaaS SLA。受邀用户隔离不等于对不可信代码的强隔离；开放任意代码执行和公众多租户前，必须完成 P1 隔离环境验收。

## 9. 数据与隐私控制

凭据仅在服务端的受限组件解密，不进入模型输入、业务日志、浏览器响应或产物。用户可以撤销连接、删除记忆、导出结果和申请删除 Workspace。

暂停与删除不同：暂停保留配置和数据；删除先禁用触发、取消运行、撤销授权，再清理内容。常规保留期限是默认配置，用户主动删除会使活动数据立即不可读取，异步删除在线内容目标 ≤ 24 小时；备份按既定生命周期淘汰，默认最多 30 天。Temporal 历史中的业务载荷使用内容引用或加密载荷，避免把必须删除的原文无控制地复制到工作流历史。

最小审计记录仅保留动作 ID、时间、决策和结果状态，不保留已要求删除的正文与凭据。法定保留要求需在实际部署地区单独评估，本稿不声称满足任何特定合规认证。

## 11. 开发里程碑

以下是基于 1–2 名熟悉技术栈开发者的 **8–10 周粗估**；单人兼职、复杂 OAuth 和生产部署可能显著延长。以完成条件推进，不按周数降低验收标准。

| 阶段 | 参考时间 | 交付 | 完成条件 |
| --- | --- | --- | --- |
| M0：基础骨架 | 第 1 周 | 账户、Workspace、模型连接、数据模型、Compose | 可登录，模型验证成功，隔离测试通过 |
| M1：一次任务 | 第 2–3 周 | Agent 版本、Run Workflow、只读工具、报告、时间线 | 手动 Run 完整交付，Worker 故障恢复通过 |
| M2：持续职责 | 第 4–5 周 | 计划、Webhook、去重、记忆、通知 | 前端离线周期执行，重复事件与调度规则通过 |
| M3：可控写入 | 第 6–7 周 | GitHub 评论、审批、动作账本、费用预算 | 精确审批、结果不明处理和超限停止通过 |
| M4：内测发布 | 第 8–10 周 | 审核 MCP、导出删除、备份、场景评测、文档 | AC-01–14 通过，受邀用户跑完整场景 |

P1 的第一个目标是在独立执行环境增加代码与浏览器，再增加 Child Run。向量检索在现有记忆确实无法满足检索需求后引入；不把它作为首版完成的前置条件。

## 12. 风险、取舍与后续决策

| 风险 / 不确定性 | v0.1 处理 | 后续验证 |
| --- | --- | --- |
| 首批用户职责过于分散 | 两个模板和固定验收场景 | 内测访谈选择主要增长场景 |
| 模型兼容能力被高估 | 原生适配 + 兼容矩阵，未知能力显式标记 | 针对具体端点增加回归用例 |
| 外部写入重试造成重复 | 动作账本 + 远端去重 / 核对，未知结果阻塞 | 测量核对成功率与人工介入率 |
| 模型支出超出估计 | 预留预算、用量状态、未知费用保守处理 | 与供应商账单比较差异 |
| 网页和工具提示注入 | 来源分层，策略在模型外执行 | 对抗样本持续扩充 |
| Temporal 学习与运维成本 | 单一编排引擎，先完成恢复场景 | 自托管与托管服务成本比较 |
| 首版计算能力有限 | 明确限定文件与内置工具 | P1 单独验证隔离代码与浏览器 |
| 产品易被当成配置台 | 总览优先展示结果和待处理事项 | 验证用户是否持续委派职责 |

后续需要用户决定的产品方向：首要用户群、最终名称、开放 SaaS 还是私有部署、团队协作优先级、优先接入的模型与应用。这些不妨碍按照本文先完成首版骨架。

## 13. 产品原则

1. 长期职责、一次运行和具体动作分别建模，用户能分别管理。
2. 模型只提出动作；平台决定是否执行，执行组件验证是否完成。
3. 用户离开页面不影响后台运行；等待时不持续消耗模型。
4. 结果、交付证据、花费和失败原因都能查看。
5. 未知能力、未知费用、未知副作用结果必须明确呈现。
6. 先让两个实际场景稳定完成，再扩展计算环境与多 Agent。
